# [Exercise 12: Hygiene](https://tfpk.github.io/macrokata/12_README.html#exercise-12-hygiene)

The `$crate` metavariable can be used to refer to the crate of where the macro was defined at.

So if you define `$crate::Widget` at crate `foo` and call at `bar`, `$crate` will expand as `foo`, unlike with using `crate::widget`

The thing that you have to note is that a macro is expanded with the context of the call site, so you have to be careful when using namespaces.

For example, when using standard structs, usually you'd use the full path `std::vec::Vec`, since it is possible that `Vec` name is overridden as another struct at the call site.

# [Exercise 11: Macro Recursion](https://tfpk.github.io/macrokata/11_README.html#exercise-11-macro-recursion)

Macros can recurse on themselves.

It is apparently quite slow, so Rust sets a default recursion of 128. This can be overridden using the crate-level attribute `recursion_limit`

> [!INFO] Currying
> Fun fact. In many functional languages, if you specify less than the required number of arguments to a function, the funciton will instead return another function with the remainder of the arguments. This concept is called **currying**.
>
> The syntax looks like `foo(arg1)(arg2)(arg3)`. If `foo` requires 4 arguments, then that function call will return a function requiring 1 argument.
>
> This feature can be replicated in Rust with macros. See the example to read further.

# [Exercise 10: Macros Calling Macros](https://tfpk.github.io/macrokata/10_README.html#exercise-10-macros-calling-macros)

Some useful builtin macros usually for custom `macro_rules` are:

- `stringify!` : Macro takes tokens and turns them into a \&str that textually represents what those tokens are
- `concat!` : Macro takes a comma-separated list of literals, and creates a \&str which concatenates them

Note if macro calls are nested, the innermost one is expanded first. e.g., with `stringify!(test!())` if `test!()` expands to `1 + 1`, we will get `"1 + 1"` instead of `"test!()"`

The `tt` fragment specifier matches a token tree. A single `tt` matches a single token. A `$($tokens:tt)` repetition matches everything, you you have to be careful with ambiguity.

One way to solve this is to "wrap" the tt repetition matcher like so:

```rust
macro_rules! my_macro {
	([$($tokens:tt),*], $expr:expr) => { ... }
}

my_macro!([a, b, c, d], other_arg)
```

An important note about "forwarding" matcher to another macros is that the fragment specifier must match the callee's. The `$ident`, `$lifetime` and `$tt` fragment specifiers are an exception, and can  be passed into a literal matcher:

```rust
macro_rules! wants_expr {
	($expr:expr) => { wants_literal!($expr) }
	// ERROR. Cannot "forward" `expr` fragment to a literal matcher. 
}

macro_rules! wants_tt {
	($tt:tt) => { wants_literal($tt) }
}

macro_rules! wants_literal {
	(3) => { ... }
}

wants_tt!(3);
wants_expr!(3);
```

# [Exercise 9: Ambiguity and Ordering](https://tfpk.github.io/macrokata/09_README.html#exercise-9-ambiguity-and-ordering)

From [rust doc](https://doc.rust-lang.org/reference/macros-by-example.html#transcribing) about matching:

1. While reading each token in the parser, there are 3 possibilities:
   1. Token found <u>matches</u>. Continue until no token left, which means the matcher is complete and the rule matces
   2. Token found <u>doesn't match</u>. Continue next rule. If no more rules, raise error
   3. The rule is <u>ambiguous</u> - i.e., it is not clear from the input token on what to do. Raise an error.
2. Once a rule matches, it starts transcribing, no more rules are examined.

```rust
macro_rules! ambiguity {
    ($($i:ident)* $j:ident) => { };
}

ambiguity!(error);
```

This errors because it is not clear what `$j` is.

Regarding ordering, consider the following example:

```rust
macro_rules! ordering {
    ($j:expr) => { "This was an expression" };
    ($j:literal) => { "This was a literal" };
}

let expr1 = ordering!('a');  // => "This was an expression".
let expr1 = ordering!(3 + 5);  // => "This was an expression".
```

The parser does not go to the literal rule, because it already matched the expr rule - <u>ordering matters</u>.

See also [[#"Literal" tokens vs separator tokens in repetition expansion]]. A concept I got confused about a bit.

> [!TIP]- Exercise hint & solution
> The match fails with
>
> ```rust
> ($($expr:expr),+ , $lastexpr:expr) => {
> 	$($expr + )+ $lastexpr
> }
> ```
>
> because the nested expr uses comma as a separator, meaning it matched ALL expessions at `sum!(1, 2, 3, 4)` including `4`, leaving `, $lastexpr` unmatched.
>
> The solution is to move `lastexpr` to the beginning of the matcher so that it matches `1`, and match the rest with `$(, $expr:expr)+`
>
> ```rust
> ($firstexpr:expr $(, $expr:expr)+) => {
>     $firstexpr $(+ $expr)*
> }
> ```

# [Exercise 7: More Repetition](https://tfpk.github.io/macrokata/07_README.html#exercise-7-more-repetition)

For multiple metavariables in one/more repetitions:

To quote [the reference](https://doc.rust-lang.org/reference/macros-by-example.html#transcribing):

> Each repetition in the transcriber must contain at least one metavariable to decide how many times to expand it.
>
> If multiple metavariables appear in the same repetition, they must be bound to the same number of fragments. For instance, `( $( $i:ident ),* ; $( $j:ident ),* ) => (( $( ($i,$j) ),* ))` must bind the same number of `$i` fragments as `$j` fragments.
>
> This means that invoking the macro with `(a, b, c; d, e, f)` is legal and expands to `((a,d), (b,e), (c,f))`, but `(a, b, c; d, e)` is illegal because it does not have the same number.

# [Exercise 6: Repetition](https://tfpk.github.io/macrokata/06_README.html#exercise-6-repetition)

Macro repetition matcher consists of 3 things:

1. <u>Group of tokens</u> we want to match
2. (Optional) a <u>separator token</u>, which tells the parser what to look for between each match
3. A <u>repetition operator</u> to indicate how many repeating patterns to match. Possible values are:
   1. `+` : ≥ 1
   2. `*` : ≥ 0
   3. `?` : 0 or 1

To create a repetition matcher:

1. <u>Start</u> with `$(`
2. The input <u>tokens</u> to match
3. <u>End</u> with `)`
4. Optional input <u>separator</u> token
5. <u>Repetition operator</u>

To use it on the transcriber:

1. Start with `$(`
2. The tokens that will be transcribed for each match
3. End with `)`
4. Optional separator token
5. Repetition operator to end

# [Exercise 5: A More Complex Example](https://tfpk.github.io/macrokata/05_README.html#exercise-5-a-more-complex-example)

Some other fragments specifiers:

- `ident`: an "identifier", like a variable name.
  Can be followed by anything.
- `block`: a "block expression" (curly braces, and their contents).
  Can be followed by anything.
- `ty`: a type.
  Can only be followed by `=>`, `,`, `=`, `|`, `;`, `:`, `>`, `>>`, `[`, `{`, `as`, `where`, or a `block` metavariable.

# [Exercise 4: Expression Metavariables](https://tfpk.github.io/macrokata/04_README.html#exercise-4-expression-metavariables)

Every metavariable is defined in form of `$<NAME>:<FRAGSPEC>`.

Fragment specifier tells what sort of Rust syntax to accept and match.

Some common fragments specifiers:

- `expr`: Matches expressions like `(3 + 2)` or `func() + CONSTANT`
- `stmt`: Matches statements like `let` or `match` statements

See [[rust-expressions-vs-statements_202606041511|Rust Expressions vs Statements]]

Macros do affect the order of operations. The expression `3 * math!(4, plus, 2)` expands to `3 * (4 + 2)`

```rust
macro_rules! math {
    () => { 3 + 4 }
}

fn main() {
    let math_result = 2 * math!();
   
    // 2 * (3 + 4) == 14
    assert_eq!(math_result, 14);
    
    // (2 * 3) + 4 == 10
    assert_ne!(math_result, 10);
}
```

Rust has a set of rules called the "follow-set ambiguity rules". These tell you which tokens are allowed to follow a metavariable (and which aren't).

For literals, this rule is simple: anything can follow a literal metavariable.

For expr (and its friend stmt) the rules are much more restrictive: they can only be followed by `=>` or `,` or `;`

Read more at https://doc.rust-lang.org/reference/macros-by-example.html#follow-set-ambiguity-restrictions

# [Exercise 3: Literal Metavariables](https://tfpk.github.io/macrokata/03_README.html#exercise-3-literal-metavariables)

Metavariables captures part of the content inside the macro matcher, and lets you reuse it inside the transcriber block.

```rust
macro_rules! do_thing {
    (print $metavar:literal) => {
        println!("{}", $metavar)
    };
}
```

So `do_thing!(print 3)` will expand to `printlnl!("{}", 3)`.

The actual type does not matter in the macro definition. Rust just needs to know what kind of syntax to expect.

If the wrong type is passed into the transcriber, Rust will throw a compiler error as if we were writing the macro without the expansion.

# [Exercise 2: Numbers](https://tfpk.github.io/macrokata/02_README.html#exercise-2-numbers)

```rust
macro_rules! torf {
    (t) => {
        true
    };
    (f) => {
        false
    };
}
fn main() {
let _true = torf!(t);
let _false = torf!(f);
}
```

Macros try to find the first rule that matches, and replaces the contents at the call site with the contents of the transcriber block.

# [Exercise 1: My First Macro](https://tfpk.github.io/macrokata/01_README.html#exercise-1-my-first-macro)

The simplest form of macro looks like this:

```rust
macro_rules! my_macro {
    () => {
        3
    }
}

let _value = my_macro!();
```

Terms:

- **Rule**: The entire arm `() => { 3 }`
- **Matcher**: The condition at the left side of the match arm - the `()`
- **Tokens**: The content insidide the condition
  If we have `(hello world)` as the matcher,
  `hello` and `world` would be the tokens
- **Transcriber**:
  The content inside the curly braces. The code Rust will replace the call site with.
